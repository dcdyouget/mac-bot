# v1.0 更新说明

> 记录 v1.0 相对之前设计的改动。每条写清楚改了什么、为什么、影响哪些文档和模块。实现状态：**仅文档，尚未实现**。

## 2026-10-11 记忆与上下文改造

**目标**：用户只管一直和 Bot 对话，不用考虑开新会话；上下文管理在后台完成；记忆变化能实时生效。

### 改了什么

| # | 之前 | 现在 | 权威位置 |
|---|------|------|---------|
| 1 | 记忆在 run 中暂存，run 成功结束才提交；提交失败只写服务端日志 | `memory` 工具调用时立即提交，返回条目 id、新版本号、剩余配额；失败直接返回给模型并发事件 | PLAN 5.5.1、5.5.5 |
| 2 | 并发修改后写的直接覆盖 | replace / remove 带 `expected_version`，版本不符返回冲突和当前内容 | PLAN 5.5.1 |
| 3 | 选中范围的记忆全部放进 L2 | L2 只放核心记忆（用户记忆 + Bot 经验）全文，项目记忆和工作记录只放目录，正文按需 `memory_search` | PLAN 5.5.1、5.5.4 |
| 4 | run 进行中看不到记忆变化；记忆被改会让快照过期并开新段 | 每次调用模型前检查全局版本，把可见范围内的变化作为增量消息追加到上下文；L0–L2 段内不变 | PLAN 5.5.3 |
| 5 | 开新段时的「记忆提取」只写在文档里，代码未接入 | 80% 压缩时先跑记忆提取，再摘要，再用最新记忆重建 L2，清掉旧增量消息 | PLAN 5.5.3 |
| 6 | 无条目版本号、无修改日志 | 条目带 `version`；新增只追加的 `data/memory/changelog.jsonl`；每段记录 `seen_revision`；按最小已读位置 + 7 天保留清理 | PLAN 5.5.7 |
| 7 | 整个上下文是一个 system 字符串，没有缓存断点 | L0–L2 与 L3–L4 拆成两个 system block，Anthropic 在 L2 末尾加 `cache_control` | PLAN 5.5.4 |
| 8 | 工作记录原样存整轮回复 | 存提炼后的「做了什么、结果如何」 | PLAN 5.5.5 |

| 9 | 任何 Bot 都能写用户记忆 | 用户偏好只由独立的整理线程 curator（只看用户本人消息，批量处理）和用户本人写；Bot 不写 | PLAN 5.5.9 |
| 10 | 没有用户档案 | 新增用户档案（称呼、语言、身份可选；时区取 Host），首次连接时主 Bot 对话式初始化 | PLAN 5.5.8 |
| 11 | 「核心记忆」没有明确定义 | 核心记忆 = 用户档案 + 用户偏好 + 本 Bot 经验，约 4,000 字以内，全文进 L2 | PLAN 5.5.1 |

### 为什么
- 原来的暂存提交会静默覆盖别人的修改，提交失败时整批丢失且无人知道。
- 全部按需调取会让模型忘记偏好，且新旧查询结果并存；全部放 system 又无法实时更新。分层 + 增量消息兼顾两者，并保持 prompt cache 稳定。

### 影响的模块
- **server**：`macbot-memory`（版本号、修改日志、立即提交）、`macbot-gateway`（增量消息、记忆提取接入、上下文拆块）、`macbot-providers`（缓存断点）。
- **protocol**：`memory` 工具和增量消息是服务端内部的，不涉及协议。用户记忆页面的协议见 PROTOCOL 5.10a（另一次提交）。待定：curator 写入的条目在 `source.by` / `updated_by` 里如何表示（现在只有 bot / user）；用户档案是否在设置里展示。
- **客户端**：本次改动不涉及；设置里的用户记忆页面单独设计。

### 已定细节
- `memory` 工具返回值：成功返回 `entry_id`、`version`、`revision`、`remaining_chars`；失败返回 `quota_full` / `conflict` / `not_found` 及当前内容（PLAN 5.5.1）。
- 增量消息：`<memory_update revision="…">` 文本块，放在下一条 user 消息或 tool_result 最前面；同一条目只保留最终状态；不通知 Bot 自己写的修改；大块记忆只给 id 和主题（PLAN 5.5.3）。
- 每段增量消息累计上限 1,000 字，超出即开新段重建 L2。
